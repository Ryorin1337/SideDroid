# 延迟与降档诊断

反馈卡顿、延迟或反复降档时，附上 `%LOCALAPPDATA%\SideDroid\host.log` 和 `adb logcat -s SideDroid` 的输出，并注明电脑显卡、手机型号、连接方式、分辨率、刷新率和编码器。USB 与 Wi-Fi 都偏慢时，也要检查两种连接共用的采集、编码、解码和显示路径。

## rate 日志

Host 在码率下降，或帧率、编码比例发生变化时写入 `rate:` 记录；只提高码率不会产生这条日志。它包含设备名、前后码率、前后帧率、前后编码比例，以及触发调整时的反馈：

| 项目 | 含义 |
|---|---|
| `queue` | 根据延迟梯度估计的排队增长，相对近期最低基线，单位 ms |
| `gradient` | 本非空窗口与上一非空窗口的平均到达延迟之差，单位 ms |
| `loss` | 当前窗口的 UDP 丢包率，不是 FEC 修复后的画面丢失比例 |
| `dropped` | 传输不可恢复丢帧和 Android 解码过载反馈；本地过载按恢复事件记数，不是精确清除帧数 |
| `backlog` | Host 应用层发送队列按当前码率换算的积压时间，单位 ms；不是 TCP 内核队列测量值，UDP 路径为 0 |
| `decode` | 最近一次完整帧接收到解码输出可用的时间，单位 ms，含本地队列和输入缓冲等待 |
| `rtt` | 最近一次 Ping/Pong 的往返时间，单位 ms |

`queue` 或 `backlog` 持续偏高，说明控制器观察到了等待增加；`dropped` 也可能来自手机端解码过载，不能把每次降档都归因于 Wi-Fi 丢包。具体门限与恢复顺序见 [码率控制](ratecontrol.md)。

## 时间口径

协议中的延迟字段以微秒传输，日志把它们除以 1000 显示为 ms。`decode` 是最近样本，不是这个窗口的平均值，向 Client 上报发生在下一帧接收时，可能略有滞后。它到解码输出为止，不含 Android 合成、屏幕呈现或扫描时间。

界面显示的 RTT、日志中的 `queue`、`decode` 都不是完整的端到端画面延迟，也不能简单相加得到它。真正比较画面或触摸响应，需要在相同分辨率、刷新率、编码器和画面内容下，观察从输入或主机画面变化到手机实际显示的时间。

## 当前源码与验证

当前源码修复了延迟统计窗口的跨线程错配，避免虚假的拥塞反馈反复压低码率和帧率；Android 端收包与解码输入分离，限制待解码积压，并优先显示最新解码输出。实现分别见 [码率控制](ratecontrol.md) 和 [Android 解码与显示](android.md)。这些源码改动尚未发布，下载既有 Release 不会自动包含它们。

自动化验证应包括 Windows 构建、`ctest --test-dir build -C Release --output-on-failure`，以及 Android 所有目标 ABI 的 release 构建。单元测试覆盖统计、码率控制和解码队列，不能替代真机端到端延迟测试，也不能证明某款设备的低延迟选项有效。真机验证应检查 USB 和 Wi-Fi、持续运动画面、旋转或切换显示设置、短暂过载后的恢复，并记录日志与实际画面延迟。
