# 协议

所有整数都是小端序。实现在 `core/`，手机端和 PC 测试工具共用同一份代码。

## 连接流程

1. 手机通过 TCP 连接端口 27183。USB 模式下目标是 `127.0.0.1`，由 `adb reverse` 转发到电脑。
2. 握手，见下文。
3. 手机发送 `Hello`。Wi-Fi 模式下 Host 回 `UdpSetup`，手机向该端口发探测包，Host 由此得知视频发往哪里。
4. Host 发送 `Config`，然后开始发帧，第一帧总是关键帧。

Host 最多同时服务 4 台设备，每台各有自己的连接、编码器和码率控制。每台的码率控制各自运行，共用 Wi-Fi 时也能分得公平，没有集中的带宽分配。

- **第 5 台：** 握手和 `Hello` 之后，Host 回一个带原因的 `Bye` 并关闭连接。
- **同一台设备再次连接：** 按 `clientId` 识别，新连接接管旧连接，不占新名额。旧连接往往是已经失效、但 Host 还不知道的那条。
- **全零的 `clientId`：** 只有测试工具会用，不做识别，设置也不保存。

控制消息始终走 TCP。视频在 USB 模式下走 TCP，在 Wi-Fi 模式下走 UDP。

## 握手

X25519 临时密钥结合预共享密钥（PSK）：

```
C -> H: "SDH1" | mode(1) | clientId(16) | clientPub(32)
H -> C: hostPub(32)
C -> H: confirmClient(32)
H -> C: confirmHost(32)
```

- `transcript = BLAKE2b(magic | mode | id | clientPub | hostPub)`
- `master = BLAKE2b(key=psk, X25519(...) | transcript)`
- 各子密钥为 `BLAKE2b(key=master, label)`。

| mode | PSK 来源 | 限制 |
|---|---|---|
| 0 USB | 全零 | Host 只接受来自回环地址的连接 |
| 1 配对 | Argon2id（16 MiB，2 轮）作用于一次性配对码 | 配对码 40 位，2 分钟有效，最多尝试 5 次 |
| 2 已配对 | 上次配对保存的 `pairSecret` | 按 `clientId` 查找 |

客户端先证明自己知道 PSK，所以猜错配对码的一方拿不到任何可用于离线验证的 Host 响应。Host 的 PSK 确认只在客户端通过验证后才发出。

**已知局限：**
- USB 模式不认证 Host。手机上的恶意应用如果抢先监听本地端口，可以冒充 Host；电脑上的本地程序也能以 USB 模式连接。
- 这套握手是为本项目定制的，用的都是成熟算法，但没有经过第三方审计。

## 加密

- **TCP 记录：** `len(4) | mac(16) | ciphertext`，算法 XChaCha20-Poly1305，nonce 由递增序列号生成，长度作为附加认证数据。
- **UDP 包：** `seq(8) | mac(16) | ciphertext`，序列号作为附加认证数据，接收端用滑动窗口拒绝重放。
- 手机的探测包使用 2^63 以上的序列号，与 Host 的序列号空间分开，避免 nonce 重复。Host 只有在探测包通过认证后才会更新视频目标地址。

## 消息

第一个字节是类型。

| 类型 | 方向 | 内容 |
|---|---|---|
| 1 Hello | C→H | 协议版本、设备名、屏幕尺寸、DPI、解码能力、刷新率列表、是否要 UDP |
| 2 Config | H→C | 显示尺寸、编码尺寸、帧率、编码格式、码率、是否镜像、用户的手动设置、画面适配。之后的第一帧是关键帧。只改画面适配时会单独重发，流本身不重建 |
| 3 Frame | H→C | 帧号、采集时间、是否关键帧、Annex B 码流 |
| 4 Stats | C→H | 约每 100ms：字节数、帧数、收包数、丢包数、丢帧数、延迟变化、解码耗时、RTT |
| 5 Touch | C→H | 多点触控，坐标为 0..65535 的归一化值 |
| 6 KeyframeRequest | C→H | 请求关键帧 |
| 7 SetDisplay | C→H | 手动设置分辨率、刷新率、码率上限（0 表示自动），副屏或镜像，以及画面适配（旧客户端不发，表示不变） |
| 8/9 Ping/Pong | 双向 | 测 RTT |
| 10 Nack | C→H | 请求重传指定分片 |
| 11 UdpSetup | H→C | Host 的 UDP 端口 |
| 12 Bye | 双向 | 主动断开。Host 发出时可带 1 字节原因，1 表示设备数已满，旧客户端会忽略它 |
| 13 Viewport | C→H | 屏幕旋转或尺寸变化 |
| 14 DisplayOptions | H→C | 手机和电脑的尺寸、推荐和当前缩放、可选的分辨率列表 |

## UDP 分片和 FEC

每帧切成 1180 字节的分片，每 32 个数据分片为一组，按当前丢包率追加 5%~30% 的 Reed-Solomon（GF(256)，Cauchy 矩阵）校验分片。

分片包头 18 字节：帧号、帧大小、组号、组数、分片号、数据分片数、校验分片数、标志。

接收端按顺序交付：
- 分片丢失时，8ms 后发 Nack。
- 超过 120ms 仍不完整的帧会被丢弃，然后请求关键帧。关键帧也丢失时每 500ms 重新请求一次。

## 码率控制

`RateController` 不依赖时钟和 I/O，可以直接单元测试。

**拥塞信号：** 丢帧、单窗口丢包率 ≥10%、排队时延 >25ms，或发送端积压 >40ms。低于 10% 的随机丢包交给 FEC 处理，不降码率。

**降级顺序：** 码率（每次 ×0.8）→ 帧率（减半，最低 30）→ 编码分辨率（85% → 70% → 50%）。

**没有流量的窗口：** 不算任何信号，目标保持不变。否则显示重建或驱动重启期间码率会涨回起始值，所有设备恢复时一起超发，又被判拥塞。

**恢复：** 按相反顺序。码率每秒约上升 5%，并且只在实际用量超过目标一半时才上升，空闲桌面不算证据。

## 显示布局

通过 Windows CCD API（`QueryDisplayConfig` / `SetDisplayConfig`）管理，实现在 `host/src/topology.cpp`。

- **多台设备：** 每台设备独占驱动的一个显示器，按显示器设备路径识别，因为 GDI 名称在驱动重载后可能变化。显示器数量随设备增加，全部断开后才减少。每次增加都要重启驱动并打断所有设备，所以一次算上所有已连接和正在连接的设备。用户自己安装的驱动不改数量，也不会被禁用。
- **虚拟屏的生命周期：** 没有设备时驱动设备是禁用的，系统里没有虚拟屏。第一台设备连接时启用，最后一台离开 5 秒后禁用，只用镜像时不启用。开机时服务也会禁用一次，防止断电后残留。
- **显示服务：** 启用和禁用设备需要管理员权限，所以由 `sidedroid-service.exe`（SYSTEM）完成，管道是 `\\\\.\\pipe\\SideDroidDisplayService`，只对本机交互式用户开放。客户端只能发送 `enable`、`disable`、`restart` 之一，没有其他参数，只作用于硬件 ID 为 `Root\\MttVDD` 的设备。回复一行错误码，0 表示成功。
- **显卡：** 虚拟屏由哪张显卡渲染，取决于配置里的 `<gpu><friendlyname>`，所有虚拟屏共用，改动后驱动要重启。选中的显卡不存在时用 `default`。编码器按设备选择，值是 `nvenc|显卡名` 或 `mf|显卡名`，空表示自动；所选的不可用时自动选择，串流不中断。编码器和画面不在同一张显卡时，每帧都要经系统内存拷贝。
- **配置生效：** 改完 `vdd_settings.xml` 后重启设备，驱动才会读取，这时其他设备的画面会中断约 7 秒后自动恢复。虚拟屏上有采集时，Windows 会把重启推迟到下次开机，并以 `ERROR_SUCCESS_RESTART_REQUIRED`（3011）提示，所以重启前要先停掉所有采集（`Host::stopVirtualCaptures`）。其他程序占用虚拟屏时无法重启，控制台会提示。不要用驱动自带的 `RELOAD_DRIVER` 和 `SETDISPLAYCOUNT`：它们每次都会让驱动崩溃（`mttvdd.dll` 访问冲突），Windows 只重启有限几次，用完就进入代码 43。
- **合并重启：** 重启驱动会中断所有设备，所以写配置时把其他设备接下来要用的分辨率一起写进去，几台同时改设置也只重启一次。
- **分辨率上限：** 配置里的模式太多时，驱动启动后没有任何显示器，设备状态却正常。实测 4 个显示器、6 个刷新率时，14 种分辨率可用，15 种不行，所以超过上限时删除最旧且没有设备在用的分辨率。
- **副屏：** 第一台设备连接时先保存当前布局，再把虚拟屏放到独立的 source 上。Windows 可能把新显示器放进复制组，那时它和主屏共用一个 source，改模式会同时改到主屏，所以 Host 拒绝修改任何含有真实显示器的输出。
- **位置：** 每台设备分开记录。用户在 Windows 显示设置里拖动虚拟屏后，Host 约 200ms 内发现新位置，更新触控映射并记下来。改分辨率、刷新率或转动手机时，它留在原来的一侧，贴着原来相邻的显示器；放不下时才移到所有显示器的右边。下次连接时回到记下的位置。
- **镜像：** 不使用 Windows 的复制模式，直接采集主屏，这台设备的虚拟屏不上桌面，主屏的任何设置都不变。同一进程不能对一个输出调用两次 `DuplicateOutput`，所以由 `CaptureHub` 的一个线程采集，通过共享纹理分发给每台设备，各自编码。
- **恢复：** 设备离开 5 秒后，它的显示器才离开桌面，短暂掉线不会让窗口跳来跳去。最后一台离开后恢复保存的布局。布局同时写入 `%LOCALAPPDATA%\SideDroid\display-layout-to-restore.bin`，程序崩溃或断电后，下次启动时恢复。
- **缩放：** 通过 `DisplayConfigSetDeviceInfo` 的未公开类型 -3 和 -4 设置，和 Windows 显示设置里的缩放是同一项，只作用于虚拟屏。推荐值取满足“逻辑尺寸至少 1280×600”且不超过手机自身密度的最大档位。
- **开机：** 驱动的显示器开机就会出现，由 SideDroid 安装驱动时，Host 启动会把它从桌面取下。

## 画面适配

画面和屏幕比例不同时怎么显示。这只和客户端有关，不影响采集和编码，但设置按设备保存在 Host（`settings.ini` 的 `fill`），所以控制台、托盘和手机显示的是同一个值。

| 值 | 名称 | 手机端的做法 |
|---|---|---|
| 0 | 适应 | 显示完整画面，留黑边 |
| 1 | 填充 | 放大到没有黑边，超出屏幕的部分裁掉 |
| 2 | 拉伸 | 铺满屏幕，比例会变 |
| 3 | 平铺 | 按原始大小重复；画面比屏幕大时先缩小到放得下 |

前三种只改变 `SurfaceView` 的大小和位置，触摸坐标按视图换算，不需要特殊处理。平铺要把一路解码输出画多次，所以改用 `SurfaceTexture` 和 OpenGL（`TiledVideoView`），只有这个模式走这条路径。平铺时每根手指属于按下时所在的那份画面，滑到相邻画面时停在边缘，不会跳回另一侧。

## 控制台管道

`\\.\pipe\SideDroidHost` 每行一个 JSON，权限只开放给当前用户，并拒绝远程连接。最多同时服务 4 个客户端。

| cmd | 参数 |
|---|---|
| `status` | 无 |
| `set` | `width` `height` `hz` `maxKbps` `allowWireless` `mirror` `scale` `fill` `encoder`，可选 `id`。带 `id` 时显示参数只改那台设备；不带时作为新的默认值应用到所有设备，并清除各设备单独的选择（位置保留）。`allowWireless` 始终是全局的 |
| `set_gpu` | `gpu`，显卡名，空表示自动。只对 SideDroid 安装的驱动生效 |
| `pair_start` / `pair_cancel` | 无 |
| `unpair` | `id` |
| `disconnect` | 可选 `id`，不带时断开所有设备 |
| `install_driver` | 无，会触发 UAC |
| `update_install` | 无，下载并校验新版本，然后启动 Windows Installer |

`status` 的 `devices` 数组列出每台已连接的设备，包含 `id`、`name`、串流数据、`settings` 和 `options`。顶层的 `settings` 是默认值，`error` 只表示 Host 自身的问题，设备的问题在各自的 `error` 里。

## 更新

仓库根目录的 `update.json`：

```json
{
  "version": "0.0.2",
  "notes": "更新说明，用 \n 换行",
  "msi": "SHA-256",
  "arm64-v8a": "SHA-256",
  "armeabi-v7a": "SHA-256",
  "x86_64": "SHA-256"
}
```

下载地址由客户端拼出，固定为 `https://github.com/Ryorin1337/SideDroid/releases/download/v<版本>/SideDroid-<版本>-x64.msi`（手机端是 `-android-<ABI>.apk`）。版本号必须是一到四段数字。校验和不一致的文件会被丢弃。

**信任范围：** 校验和和文件都来自同一个 GitHub 账号，所以账号被盗时校验和挡不住恶意 MSI。APK 还有一层保护：Android 只接受同一密钥签名的新版本。
