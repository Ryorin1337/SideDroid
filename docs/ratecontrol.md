# 码率控制

每台设备各有自己的编码器和码率控制，共用 Wi-Fi 时也独立调整，没有集中的带宽分配。`RateController` 不依赖时钟和 I/O，可以直接单元测试，实现在 [core/src/ratecontrol.cpp](../core/src/ratecontrol.cpp)。传输字段见 [协议](protocol.md)，运行日志见 [延迟诊断](troubleshooting.md)。

## 拥塞与恢复

任一条件成立就判为过载：有丢帧反馈、单窗口丢包率至少 10%、估计排队时延超过 25ms，或发送端积压超过 40ms。低于 10% 的随机丢包本身交给 FEC 处理，但同一窗口里的其他过载条件仍可触发降档。Android 本地解码过载也会反馈丢帧，收包与解码分开后仍能让 Host 降档。

**降级顺序：** 先降码率，每次乘 0.8，两次降码率之间有 3 个有效更新窗口的冷却。到达码率下限且累计 10 个过载窗口后，再把帧率减半，最低到配置下限（默认 30）；帧率已经到底时，才依次把编码比例降为 85%、70%、50%。

**恢复：** 排队低于 8ms、平滑后的丢包率低于 5%、发送积压低于 10ms 时探测余量。每个这样的窗口增加 `max(50 kbps, 当前码率 / 200)`，通常约每秒上升 5%；实际用量必须超过目标一半，或当前码率仍低于起始值。空闲桌面不能证明还有多少带宽。累计 30 个余量窗口后，先恢复编码比例，再恢复帧率；中间的保持窗口不会清空这个累计值，过载会清空。

**空窗口：** 字节数、收包数、丢包数、丢帧反馈都为 0，且没有发送积压时，目标保持不变。这样显示重建或驱动重启期间不会涨回起始码率，导致所有设备恢复时一起超发。没有新网络流量但仍有本地解码过载反馈的窗口不算空窗口。

UDP 校验比例按平滑后的丢包率在 5%、10%、20%、30% 间选择。TCP 不加 FEC；UDP 的发送端积压目前不参与控制。

## 延迟统计

Host 的采集时间和客户端的接收时间属于不同单调时钟。`DelayStats` 只测到达延迟的变化，不要求两端时钟同步，实现在 [core/src/delaystats.cpp](../core/src/delaystats.cpp)。

每个完整帧产生一个相对样本：

```text
相对延迟 = (本帧接收时间 - 首帧接收时间) - (本帧采集时间 - 首帧采集时间)
延迟梯度 = 本非空窗口的平均相对延迟 - 上一非空窗口的平均相对延迟
```

分别减去各自的时钟原点，避免很大的固定时钟偏移进入求和。采样时的总和、计数，以及统计线程的快照、清零都由同一把锁保护，避免把一个窗口的总和与另一个窗口的计数混在一起，制造虚假的排队增长。

首个非空窗口的梯度为 0。空窗口返回 0，但保留上一有效平均值；平均值本身等于 0 也是有效状态。平均值向零截断，两个平均值的差饱和到协议的 `int32` 范围，避免溢出后符号翻转。`Stats` 的线格式不变。

控制器累计这些梯度，并与缓慢上移的最低基线比较：每个有效更新窗口，基线最多上移 50 微秒。两者之差就是控制使用的排队估计，它表示相对近期低点增加的等待，不是绝对单程传输时间。

## 测试范围

[core/tests/core_tests.cpp](../core/tests/core_tests.cpp) 覆盖固定正负时钟偏移、窗口大小变化、空窗口、零平均值、极大时钟原点、梯度饱和和并发快照样本守恒，也检查恒定延迟不会触发降档、真实排队增长仍会降低码率，以及仅有本地解码丢帧反馈时仍能降档。

这些测试验证统计与决策，真实网络和解码器的表现仍需按 [延迟诊断](troubleshooting.md) 在设备上验证。
